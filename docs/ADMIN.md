# 동구랑페이 관리자 운영 매뉴얼

## 1. 서비스 구성

주민 지도는 GitHub Pages에서 운영합니다. 관리자 화면은 담당 기관이 운영하는 **별도 HTTPS 서버의 `/admin`** 주소입니다. 주민 지도에는 관리자 링크가 없습니다.

한 대의 FastAPI 서버와 SQLite DB로 업로드 비교, 승인, 주민 수정 요청, 변경 이력을 처리합니다. 별도 DB 서비스나 유료 인증 서비스는 필요하지 않습니다. **서버에 영구 저장 디스크가 필요합니다.** 무료 호스팅의 임시 디스크는 재시작 시 DB가 없어질 수 있으므로 사용할 수 없습니다. 기관의 기존 서버/저비용 VPS + 영구 디스크가 가장 단순합니다. 무료 서비스는 영구 디스크·휴면 정책을 먼저 확인하세요.

관리자 승인 → DB 반영과 주민 지도 배포는 별도 단계입니다. 서버가 중단되어도 이미 배포된 지도는 정상 작동하며 수정 요청 접수만 사용할 수 없습니다.

## 2. 처음 한 번: 서버 준비 (서버 담당자)

1. 저장소를 서버에 내려받고 Python 환경을 만듭니다.
2. `pip install -r requirements.txt`를 실행합니다.
3. `.env.example`을 참고해 서버 환경변수를 설정합니다. `.env`는 Git에 올리지 않습니다.
4. `uvicorn app.main:app --host 127.0.0.1 --port 8000 --env-file .env`로 실행하고, HTTPS 리버스 프록시 및 프로세스 자동 재시작을 설정합니다.
5. `/health` 응답이 `{"status":"ok"}`인지 확인합니다.
6. 관리자 서버 `/admin`에 접속해 관리자 인증키로 로그인합니다.

### 환경변수

| 변수 | 용도 |
| --- | --- |
| `ADMIN_KEY` | 충분히 긴 임의 관리자 인증키. `python -c "import secrets; print(secrets.token_urlsafe(32))"`로 생성 가능 |
| `DATA_DIR` | DB가 보존되는 서버 영구 디스크 경로. 기본 `data/` |
| `ADMIN_ORIGIN` | 관리자 페이지 HTTPS 출처. 예: `https://admin.example.kr` (경로 없이) |
| `ADMIN_COOKIE_SECURE` | 운영 `true`, 로컬 HTTP 확인만 `false` |
| `NTS_SERVICE_KEY` | 국세청 사업자등록 상태조회 서비스 키 |
| `KAKAO_REST_API_KEY` | 기존 주소→좌표 변환에 사용하는 서버용 키 |
| `PUBLIC_ORIGINS` | 주민 지도 출처. 기본 `https://lch854053.github.io`; 여러 출처는 쉼표 구분 |
| `RATE_LIMIT_SECRET` | 선택: 요청 제한용 IP 해시 비밀값. 없으면 `ADMIN_KEY` 사용 |
| `GITHUB_PUBLISH_TOKEN` | 선택: 배포 PR 생성용 fine-grained GitHub 토큰, 서버에만 저장 |
| `GITHUB_REPOSITORY` | 기본 `lch854053/donggurang-pay` |
| `LOAD_SAMPLE_DATA` | 운영에서는 반드시 `false` (기본값) |
| `ENABLE_WEEKLY_STATUS_CHECK` | 기본 `false`. 켜도 상태 표시만 바뀌며 자동 지도 제외하지 않음 |

공개 지도 연결: GitHub 저장소 **Settings → Secrets and variables → Actions → Variables**에서 `PUBLIC_API_BASE_URL`에 서버의 HTTPS 기본 URL을 입력하고 Pages 워크플로를 실행합니다. 이 값은 주민 브라우저에 공개되므로 **API 키나 토큰을 절대 넣지 않습니다.**

프록시에서 실제 IP를 전달할 때는 Uvicorn의 `--forwarded-allow-ips`에 신뢰하는 프록시 IP만 지정합니다. 인터넷에서 임의의 `X-Forwarded-For` 헤더로 요청 제한을 우회할 수 없게 합니다. IP는 비밀값을 섞은 해시와 요청 횟수만 DB에 저장하며 원본 IP는 요청 내용에 저장하지 않습니다.

## 3. 처음 한 번: 현재 지도와 원본 명단 연결

현재 정적 지도에는 사업자등록번호가 없습니다. **현재 지도를 작성한 원본 기준 명단**을 서버에서 읽어 공개 지도 ID와 사업자번호를 연결해야 합니다. 최신 월별 명단으로 초기화하면 빠진 업소를 연결할 수 없으므로 초기화가 중단됩니다.

1. 빈 운영 DB에서 관리자 로그인합니다.
2. **월별 명단 비교 → 최초 운영: 원본 명단 연결**을 펼칩니다.
3. 기존 지도 작성에 사용한 원본 `.xlsx` 또는 `.csv`를 선택합니다.
4. **초기 연결**을 누릅니다.
5. `3,762개 원본 연결 완료`를 확인합니다.

상호명·상세주소가 정확하게 일치해야 합니다. 기존 중복 제거 감사 기록도 함께 사용해 병합된 주소·이름을 연결합니다. 한 공개 가맹점에 원본 사업자번호가 여러 개 연결된 경우도 서버에서만 보존합니다. 지도 ID, 좌표, 업종/상호 별칭과 전화번호는 그대로 유지합니다. 원본 파일은 서버 파일로 보관하지 않고 허용된 필드만 DB에 저장합니다.

일부 항목이 연결되지 않으면 **전체 초기화를 취소**하며 누락 지도 ID를 표시합니다. 원본 버전·주소·상호를 확인한 뒤 다시 시도하세요. 임의로 누락 가맹점을 삭제해서 초기화를 통과시키지 마세요.

### 기존 FastAPI DB가 있는 경우

서버 실행 시 테이블은 기존 DB에 추가되고 기존 레코드는 지우지 않습니다. 하지만 과거 DB의 가맹점 ID와 현재 Pages의 지도 ID가 다를 수 있습니다. Pages 연동 운영에는 다음 이전 절차를 사용합니다.

1. 기존 서버를 중단하고 DB를 안전하게 백업합니다.
2. 기존 DB를 삭제하지 않고 **새 영구 디렉터리**를 `DATA_DIR`로 설정합니다.
3. `LOAD_SAMPLE_DATA=false`로 새 서버를 실행합니다.
4. 위의 원본 명단 연결을 수행하고 ID·전화번호를 확인합니다.
5. 기존 DB/업무 자료는 비공개 백업으로 보관합니다.

원본 기준 파일이 없는 상태에서는 최신 명단을 안전하게 비교할 수 없습니다. 원본 확보가 필요합니다.

## 4. 월별 가맹점 업데이트

1. 관리자 `/admin`에 접속하고 인증키로 로그인합니다.
2. **월별 명단 비교**에서 최신 `.xlsx`/`.csv`를 선택합니다.
3. **업로드 및 자동 비교**를 누르고 분석 완료를 기다립니다. 수천 건 조회는 수 분 걸릴 수 있습니다.
4. 파일명과 요약 숫자를 확인합니다.
5. **신규 후보** 필터에서 상호·주소·업종·상태·좌표·전화번호를 확인합니다.
6. 추가할 항목을 체크합니다. 머리글 체크박스는 **현재 페이지의 승인 가능 항목**을 일괄 선택합니다. 다음 페이지에서 선택을 추가할 수 있습니다.
7. 사유를 적고 **선택 항목 승인**을 누릅니다. 확인창에서 신규/변경/삭제 건수를 다시 확인합니다.
8. **정보 변경** 필터에서 이전/업로드 값을 비교하고 승인합니다.
9. **삭제 검토 후보**에서 폐업 여부, 최신 명단 미포함, 현재 지도 등록 정보를 확인합니다. 필요할 때만 체크하여 승인합니다.
10. 적용하지 않을 항목은 체크하고 **선택 항목 반영하지 않음**을 누릅니다.
11. **변경 이력**에서 추가·변경·지도 제외 및 사유를 확인합니다.
12. **지도 배포**에서 공개 파일 생성·PR 생성·검증·병합을 진행합니다.
13. 배포 성공 후 주민 지도를 새로 열어 표본 가맹점을 확인합니다.

실수로 제외한 가맹점은 **가맹점 관리**에서 검색해 **지도에 복원**할 수 있습니다. 기록은 지우지 않습니다. 복원도 담당자 승인 및 별도 배포가 필요합니다.

### 업로드 컬럼

필수: `사업자번호`, `가맹점번호`, `가맹점명`, `사업장주소`, `가맹점업종명`.

선택: 원본의 `사업자 상태` 등 기존 허용 컬럼. 대표자명·휴대전화 컬럼은 버립니다. 임의의 개인정보 컬럼, 저장 대상 필드에 들어 있는 개인정보 패턴, 수식, 매크로·외부 연결·내장 파일은 차단합니다. 확장자는 `.xlsx`, `.csv`만 지원하며 `.xls`는 `.xlsx`로 저장한 뒤 사용합니다. 파일은 최대 10MB입니다.

전화번호는 업로드 파일에서 수집하지 않습니다. 기존 연결 전화번호는 유지하며 필요한 변경은 담당자가 **가맹점 관리**에서 확인한 영업 연락처로 수정합니다.

### 상태 설명

| 상태 | 의미 / 처리 |
| --- | --- |
| 유지 | 같은 사업자와 같은 가맹점 정보. 중복 생성하지 않음 |
| 정보 변경 | 같은 사업자이나 상호·주소·업종이 다름. 이전/이후 비교 후 승인 |
| 신규 후보 | 기존 사업자 연결 없음. 국세청 계속사업자이며 좌표가 확인돼야 추가 승인 가능 |
| 폐업으로 등록 제외 | 신규 사업자가 폐업. 추가 승인 불가. 원본 폐업 상태도 외부 API의 계속사업자 응답으로 덮어쓰지 않음 |
| 삭제 검토 후보 | 기존 지도에 있지만 최신 명단에 없음. 폐업·계속사업자·조회 실패 모두 자동 삭제하지 않음 |
| 확인 필요 | 동일 사업자번호에 서로 다른 정보/여러 업소가 있어 자동 판단 불가, 또는 이전 제외 업소의 재등장. 가맹점 관리에서 개별 확인 |
| 좌표 확인 필요 | 주소 좌표 변환 실패. 신규/변경 승인 불가. 주소를 확인하고 재검증 |
| 조회 실패 / 휴업 / 미등록 | 신규 추가 승인 불가. API 설정·상태를 확인한 뒤 재검증 |
| approved / rejected | 해당 후보 승인됨 / 반영하지 않음 |

국세청·좌표 재검증은 미처리 신규/변경 후보에 사용합니다. 상단 요약은 **처음 업로드한 시점**이고 현재 표의 상태가 재검증 결과입니다. 다른 업로드 승인 또는 가맹점 개별 수정으로 DB가 바뀌면 이전 비교는 사용 불가가 됩니다. 최신 명단을 다시 업로드해 비교하세요. 같은 업로드의 일부 승인 후에는 나머지 후보를 계속 승인할 수 있습니다.

동일 사업자번호의 동일 내용은 후보 하나로 묶습니다. 사업자번호가 같아도 서로 다른 주소·상호가 있으면 임의로 합치거나 여러 가맹점을 생성하지 않고 확인 필요로 둡니다. 이미 다른 지도 ID에 연결된 사업자의 변경도 확인 필요로 처리합니다.

상충하는 업로드 정보는 표에 모두 표시됩니다. 기존 업소는 가맹점 관리에서 확인·수정하고, 아직 등록되지 않은 신규 업소의 상충 정보는 원본 명단을 확인·정정한 뒤 다시 업로드합니다.

주소 변경 시 기존 좌표를 재사용하지 않습니다. 검증된 새 좌표가 필요하며 이전 주소의 전화번호·위치 설명은 제거합니다. 상호/업종 변경 시 이전 별칭은 새 정보와 상충하지 않도록 정리합니다.

## 5. 주민 수정 요청 처리

주민은 가맹점 카드의 **정보 수정 요청**을 눌러 유형과 추가 내용을 보냅니다. 이름·전화번호·이메일은 필수로 받지 않습니다. 서버가 해당 지도 ID의 상호명·주소를 자동 기록합니다. 사업자번호는 주민에게 보여주지 않습니다.

1. **주민 수정 요청** 탭에서 미처리/유형 필터와 검색을 사용합니다.
2. 같은 가맹점·유형의 미처리/확인 중 건수를 함께 확인합니다.
3. 확인 중으로 바꾸고 확인 내용을 저장합니다.
4. 필요하면 **가맹점 확인·수정**을 눌러 기존 정보와 바꿀 정보를 비교합니다.
5. 정보 수정, 지도에서 제외, 지도에 복원 중 작업을 선택합니다.
6. 사유를 적고 최종 승인합니다. 요청 ID는 자동 연결됩니다.
7. 요청 상태를 **반영 완료** 또는 **반영하지 않음**으로 저장합니다.
8. 실제 지도 정보가 바뀌었으면 지도 배포까지 진행합니다.

요청의 처리 상태 변경만으로 가맹점을 삭제하지 않습니다. `반영 완료`는 담당자 업무 처리 완료 표시이며 Pages 배포 상태와 별도입니다. 공개 지도 반영은 배포 성공을 확인해야 합니다.

공개 요청에는 IP별 분당 3건·하루 20건 제한, 입력 길이 검증, HTML/script 거부, 숨은 스팸 필드 검사를 적용합니다. 담당자는 내용에 적힌 불필요한 개인정보를 별도로 복사·배포하지 마세요.

## 6. 주민 지도 배포

### 권장: 배포 PR

서버 담당자가 GitHub fine-grained 토큰을 만듭니다. 해당 저장소에만 **Contents: Read and write, Pull requests: Read and write** 권한을 주고 서버의 `GITHUB_PUBLISH_TOKEN`에 보관합니다. Workflow 쓰기 권한은 필요하지 않습니다.

1. **지도 배포 → 승인 데이터로 공개 파일 생성**을 누릅니다.
2. 파일 번호·데이터 버전을 확인합니다.
3. **배포 PR 생성**을 누릅니다.
4. 표시된 GitHub PR 링크를 엽니다.
5. `Validate public snapshot` 검증이 성공했는지 확인합니다. 저장소 보호 규칙에서 이 검증을 필수로 지정하는 것을 권장합니다.
6. PR을 병합합니다.
7. Actions의 `Deploy merchant map to GitHub Pages` 성공을 확인합니다.
8. 주민 지도에서 표본을 확인합니다. 기존 열린 페이지는 버전 확인 후 새로고침됩니다.

PR에 들어가는 변경은 `static/merchant-data.js` 하나입니다. 사업자번호·관리자 키·국세청 키·업로드 원본·민원 내용은 들어가지 않습니다. 공개 파일에는 승인된 상호·주소·업종·좌표·전화번호 등만 담깁니다. 현재 전화번호 오버레이보다 승인 파일의 전화번호가 우선합니다.

새 버전 생성 후 DB에서 다른 변경을 승인했다면 파일을 다시 생성합니다. 이전 PR이 남아 있으면 최신 PR만 병합하고 이전 PR은 닫습니다. 버전 역행은 검증에서 차단됩니다.

### GitHub 토큰을 사용하지 않는 경우

공개 파일을 다운로드하고 담당 개발자가 `static/merchant-data.js`로 반영해 검증·PR·병합·Pages 배포를 수행할 수 있습니다. 브라우저에서 JSON 파일을 직접 수정하는 방식은 아닙니다. 승인된 DB에서 생성한 파일만 사용합니다.

### 실패 시

- PR 생성 실패: DB 승인은 보존됩니다. 기존 공개 지도는 유지됩니다. GitHub 토큰·권한·네트워크를 확인하고 같은 파일로 재시도합니다. 이미 생성된 브랜치/PR이 있으면 재사용합니다.
- 검증 실패: PR을 병합하지 말고 오류를 확인합니다.
- Pages 배포 실패: 기존 성공 배포는 유지됩니다. Actions 오류를 확인하고 재실행합니다.
- 화면이 이전 버전: 새로고침하거나 배포 커밋을 `?v=커밋해시`로 붙여 새로 엽니다.

관리자 표의 `pr_created`는 PR 생성 상태입니다. 실제 PR 병합/Pages 성공 여부는 GitHub에서 확인해야 합니다.

## 7. 백업·인수인계

- 월별 작업 전 DB를 백업합니다. 서버가 쓰는 중에는 SQLite 백업 API를 사용해 WAL 데이터까지 포함합니다.
- 예시: `python -c "import sqlite3; s=sqlite3.connect('/영구경로/merchants.db'); d=sqlite3.connect('/비공개백업/merchants-202610.db'); s.backup(d); d.close(); s.close()"`.
- 백업에는 사업자번호와 주민 요청이 있으므로 공개 저장소/Pages에 올리지 않습니다. 서버 디렉터리와 백업의 접근 권한을 담당자에게만 부여합니다.
- 인수인계: 관리자 URL, 기관 서버 위치, 백업 경로, API 키 발급 계정, GitHub 담당 계정, 월별 원본 기준 파일 위치를 전달합니다. 비밀값은 별도 안전한 채널로 전달합니다.
- 인증키 변경 후 기존 세션을 폐기하려면 서버를 중단하고 DB의 `admin_sessions`를 비운 후 재시작합니다. 로그인 세션은 8시간 만료됩니다.
- 테스트 예제 사업자는 운영에 넣지 않습니다. 운영 데이터 최초 연결은 반드시 원본 기준 명단으로 합니다.
